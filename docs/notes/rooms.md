# Room Architecture & Technical Design Notes (Task T05)

## 1. Overview & Data Model
Task T05 transitions PairPrep's room management from in-memory ephemeral state to MongoDB persistence across the data models established in T03:
- `rooms`: Stores room configuration (`title`, `slug`, `type`, `language`, `status`, `memberCount`, `memberCountUpdatedAt`, `lastActivityAt`, `idempotencyKey`).
- `room_members`: Stores participant records (`roomId`, `memberId`, `displayName`, `role`, `isGuest`, `guestExpiresAt`, `joinedAt`, `lastSeenAt`).
- `guests`: Ephemeral guest identities auto-expired via MongoDB TTL index (`expiresAt: 7 days`).
- `idempotency_keys`: Strict deduplication state with active lease fencing (`startedAt`, `status`, `statusCode`, `response`, `requestHash`).

All room identifiers exposed over HTTP use cryptographically unguessable slugs with at least 128 bits of CSPRNG entropy (`crypto.randomBytes(16).toString("base64url")`), regex matching `^[A-Za-z0-9_-]{16,}$`. Slugs are never reflected back in error messages or logs to prevent information leakage.

## 2. Identity & Guest Cookie Security (`AUTH-3`)
PairPrep supports dual-identity participation across authenticated users and anonymous guests:
1. **Signed-in User Precedence**: If a request carries a valid session cookie (`pairprep.sid`), `req.principal` resolves to `{ type: "user", id, displayName, email, role }`. Signed-in users always take strict precedence over any guest cookie present on the request.
2. **HMAC-Signed Guest Cookie (`pairprep.guest`)**:
   - Format: `<guestId>.<base64url_hmac>`
   - Key derivation uses domain separation via HMAC with a dedicated label:
     `key = crypto.createHmac("sha256", SESSION_SECRET).update("pairprep.guest-cookie-signing-v1").digest()`
   - Constant-time HMAC comparison: `crypto.timingSafeEqual` prevents side-channel timing attacks.
   - Database validation: Even if the signature matches, the server verifies the guest record exists in MongoDB and has not expired.
   - Tamper response: An invalid or expired guest cookie causes immediate cookie clearance (`res.clearCookie`) and treats the request as anonymous (returning 401 on protected routes).

### Cross-Room Guest Join Order & Single Guest Identity
A browser may only hold one guest identity cookie at a time. When a guest navigates from Room A to Room B:
1. The new Room B guest document and membership are created **first**.
2. The new signed cookie is set on the HTTP response.
3. Cleanup of Room A (removing Room A membership and deleting old guest doc) is dispatched **afterwards** on a best-effort basis. This ensures Room B access is never blocked if Room A cleanup encounters transient latency or failures.

## 3. Concurrency & Atomic Participant Limit (`ROOM-4`, `CONC-3`)
Rooms are hard-capped at 6 active participants (1 owner + up to 5 additional participants). This cap is enforced atomically in MongoDB without multi-document transactions:
1. **Pre-allocated Owner Slot**: On room creation (`POST /api/v1/rooms`), `memberCount` is initialized to 1. The owner membership document is inserted directly without a secondary counter increment.
2. **Atomic Conditional Increment**: New participant joins execute:
   ```javascript
   RoomModel.findOneAndUpdate(
     { _id: roomId, memberCount: { $lt: 6 }, status: "open" },
     { $inc: { memberCount: 1 }, $set: { memberCountUpdatedAt: new Date() } },
     { new: true }
   );
   ```
   If `memberCount` is already 6, the update matches zero documents.
3. **Fenced Self-Healing (>60s)**:
   If an increment fails because the room appears full, the server checks `memberCountUpdatedAt`. If the timestamp is older than 60 seconds (guarding against race conditions with concurrent joins), the server recounts actual documents in `room_members`. If `actualCount < 6`, a fenced atomic update resets `memberCount` to `actualCount` and retries the increment.
4. **Member Insert Compensation & E11000 Handling**:
   - If a member insertion fails, `memberCount` is decremented back.
   - If duplicate concurrent joins occur for the same principal, the unique index on `{ roomId: 1, memberId: 1 }` catches E11000, decrements the redundant increment, and returns the existing member document.
   - If owner member insertion fails during room creation, compensation triggers immediate deletion of the orphaned room document.

## 4. Idempotency Middleware (`CONC-3`)
Mutating operations (`POST /rooms`, `PATCH /rooms/:slug/members/:id`, `POST /rooms/:slug/end`, `DELETE /rooms/:slug`) support the `Idempotency-Key` header with lease-based deduplication:
- **Canonical Hash**: Generated by hashing `method + ":" + pathWithParams + ":" + canonicalStringify(sortedBodyKeys)`.
- **Active Lease & Stale Takeover**:
  When a key is reserved, it enters `in_progress` with `startedAt = new Date()`. If a crash occurs mid-flight and the lease exceeds 30 seconds, subsequent requests atomically take over the lease:
  ```javascript
  IdempotencyKeyModel.findOneAndUpdate(
    { key, actorId, route, status: "in_progress", startedAt: { $lt: new Date(Date.now() - 30000) } },
    { $set: { status: "in_progress", requestHash, startedAt: new Date() } }
  );
  ```
- **2xx-Only Caching**: Only successful 2xx responses are cached. Any non-2xx outcome or unexpected error deletes the key immediately, allowing instant client retry.
- **DTO Isolation**: Cached responses strictly store and return clean DTOs, stripping internal mongoose properties (`__v`, `_id`, timestamps, secrets).

## 5. Architectural Decisions & Scope Constraints
- **Unambiguous Member `:id` Semantics**: In all room participant endpoints (`PATCH /api/v1/rooms/:slug/members/:id`, `DELETE /api/v1/rooms/:slug/members/:id`), `:id` strictly represents the unique MongoDB membership document `_id` (`RoomMemberModel._id`), never the underlying principal `memberId` (user ID or guest ID). Role updates and participant removals resolve records exclusively via `roomMemberRepo.findMemberByDocId(roomId, targetId)`, and passing a user or guest ID returns 404 `MEMBER_NOT_FOUND`.
- **No Leave Endpoint in Phase 1**: Voluntarily leaving a room is not implemented in Phase 1. Disconnection is handled at the network/session level, and rooms expire or are cleaned up via inactivity archiving.
- **Kick Not Ban**: Member removal (`DELETE /api/v1/rooms/:slug/members/:id`) removes the user's active membership in the room. It does not establish a persistent ban list.
- **Inactivity Archiving (`ROOM-6`)**: Rooms with no activity (`lastActivityAt`) for 30 consecutive days are transitioned to `"archived"` status by the background maintenance job.
- **Expired Guest Member Purge**: Expired guest records are cleaned up from `room_members` via batch query on `guestExpiresAt`, decrementing `memberCount` per room in a single atomic `$inc`.
- **Cascade Deletion Emptiness**: Room deletion cascades through all 8 dependent collections in child-first order (`room_members`, `doc_updates`, `doc_snapshots`, `messages`, `events`, `client_map`, `guests`, and finally `rooms`).

## 6. How to Explain This in an Interview

### System Overview & Problem Statement
"In PairPrep, rooms represent real-time collaborative coding environments capped at 6 concurrent participants. Week 1 used an in-memory implementation that lost state on restarts and suffered from concurrency race conditions. In Task T05, I designed and built the persistence layer, role-based authorization, cryptographic guest identity system, and an atomic idempotency engine using MongoDB without requiring heavyweight distributed locking like Redis Redlock."

### Key Technical Challenges & Trade-offs
1. **Atomic Concurrency vs. Distributed Transactions**:
   - *Problem*: Multi-document transactions in MongoDB require replica sets and introduce higher latency and lock contention. How do we guarantee the 6-participant room limit under high-concurrency race conditions (e.g., 10 simultaneous joins)?
   - *Solution*: I used a conditional atomic increment (`findOneAndUpdate` with `{ memberCount: { $lt: 6 } }`). The owner's slot is pre-allocated on room creation (`memberCount: 1`). Subsequent joins conditionally increment the counter. If insertion fails due to duplicate principal joining, the unique compound index `{ roomId: 1, memberId: 1 }` catches E11000, rolls back the extra increment, and returns the existing membership.
   - *Self-Healing*: If transient failures cause counter drift, we self-heal using a fenced recount on `{ memberCount, memberCountUpdatedAt }`, but only if the timestamp is older than 60 seconds to avoid interfering with active concurrent joins.

2. **Idempotency with Lease Fencing**:
   - *Problem*: Network timeouts or client retries on `POST /rooms` or `DELETE /rooms/:slug` could lead to duplicate rooms or false 404 errors.
   - *Solution*: I implemented an atomic reservation pattern in MongoDB. The first request wins the reservation lease with a `startedAt` timestamp. If the server crashes mid-flight, a stale lease (>30s) is safely acquired by the next retry. Responses are cached exclusively on 2xx completion, while non-2xx errors delete the reservation immediately so the client can retry cleanly.

3. **Dual Identity & Cryptographic Security**:
   - *Problem*: Users can be logged-in developers (via OAuth) or temporary interview candidates (guests). We need to prevent guest cookie forgery, session hijacking, and cross-room pollution.
   - *Solution*: I implemented domain-separated HMAC key derivation from `SESSION_SECRET` with a purpose-specific label (`pairprep.guest-cookie-signing-v1`) to sign guest cookies (`<guestId>.<hmac>`). Verification uses `crypto.timingSafeEqual` to eliminate timing side-channels, combined with a MongoDB check to ensure the guest document is still valid and not expired. If a guest moves to another room, we create the new room membership first and dispatch cleanup of the old room best-effort, ensuring availability is never compromised.
